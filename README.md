# MAX Chat · GREEN-API

Веб-интерфейс для отправки и получения текстовых сообщений в мессенджере **MAX** через [GREEN-API](https://green-api.com/max).
Внешний вид основан на [web.max.ru](https://web.max.ru/): список чатов слева, переписка справа.

## Возможности

- Вход по `idInstance` и `apiTokenInstance`. Данные проверяются методом `getStateInstance`, и в чат пускает только авторизованный инстанс.
- Новый чат по номеру телефона. Принимаются форматы `+7 (999) 123-45-67`, `8 999 123 45 67`, `79991234567` и международные номера.
- Отправка текстовых сообщений методом [SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/). Enter отправляет, Shift+Enter переносит строку, длина до 4000 символов.
- Приём сообщений по технологии [HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/): `ReceiveNotification` через RTK Query с `pollingInterval`, после обработки `DeleteNotification`.
- Состояние инстанса перепроверяется раз в минуту и сразу после уведомления `stateInstanceChanged`. Если инстанс перестал быть авторизован, появляется предупреждение.
- Статусы отправленных сообщений: отправляется, отправлено, доставлено, прочитано, ошибка. Неотправленное сообщение можно отправить повторно.
- Сообщение от нового контакта создаёт новый чат, у чата появляется счётчик непрочитанных.
- История чатов хранится в `localStorage`, отдельно для каждого инстанса. Учётные данные хранятся в `sessionStorage`: они переживают перезагрузку страницы и удаляются при закрытии вкладки.
- Адаптивная вёрстка для мобильных устройств и тёмная тема.

## Стек

React 19, TypeScript, Vite, Redux Toolkit с RTK Query.

## Запуск

Нужен Node.js 20 или новее.

```bash
npm install
npm run dev          # http://localhost:5173
```

Продакшен-сборка:

```bash
npm run build
npm run preview
```

Перед входом нужно:

1. Создать инстанс MAX в [личном кабинете GREEN-API](https://console.green-api.com) и авторизовать его.
2. Для приёма входящих сообщений в настройках инстанса оставить **пустым** поле `webhookUrl` и включить уведомления о входящих сообщениях (при желании также об исходящих и о статусах). Без этого очередь `ReceiveNotification` останется пустой.
3. Если в кабинете указан персональный `apiUrl` (например, `https://1103.api.green-api.com`), ввести его в разделе «Дополнительно» на форме входа.

## Структура

Проект организован по [Feature-Sliced Design](https://feature-sliced.design): слой импортирует только из слоёв ниже, слайсы одного слоя друг о друге не знают, наружу слайс отдаёт только то, что есть в его `index.ts`. Импорты между слоями идут через алиас `@/`.

```
src/
  app/                    точка входа, стор (makeStore, сохранение истории), глобальные стили и типы
  pages/
    login/                LoginPage
    messenger/            MessengerPage, опрос очереди и состояния инстанса (useConnectionProblem)
  widgets/
    sidebar/              шапка, баннеры, форма нового чата, список чатов
    chat-window/          шапка чата, лента сообщений, поле ввода
  features/
    auth/                 LoginForm, LogoutButton, вход / выход / восстановление сессии
    create-chat/          NewChatForm
    send-message/         эндпоинт sendMessage, MessageInput, RetryButton, отправка и повтор
    receive-messages/     эндпоинты очереди, разбор уведомлений, listener
    enable-receiving/     SettingsNotice: включение приёма уведомлений в настройках инстанса
  entities/
    session/              учётные данные в сторе и в sessionStorage
    chat/                 слайс чатов и сообщений, селекторы, история в localStorage, ChatCard, MessageBubble
    instance/             эндпоинты состояния и настроек инстанса, тексты проблем
  shared/
    api/                  базовый RTK Query API и baseQuery для GREEN-API
    lib/                  телефоны, время, работа с Storage
    model/                типизированные хуки, listener middleware, AppThunk
    ui/                   Avatar, Logo, Field, FormError
```

### Решения, которые стоит пояснить

- **Поллинг и теги RTK Query.** `useReceiveNotificationQuery(receiveTimeout, { pollingInterval })` опрашивает очередь. Listener middleware ловит успешный ответ, добавляет событие в чаты и вызывает `deleteNotification`. Эта мутация инвалидирует тег `Notification`, поэтому следующее уведомление запрашивается сразу, без ожидания интервала, и очередь быстро разгружается. `sendMessage` тоже инвалидирует `Notification`, потому что вскоре после отправки приходят `outgoingAPIMessageReceived` и статусы. Уведомление `stateInstanceChanged` инвалидирует тег `Instance`, а `setSettings` инвалидирует `Settings` и `Instance`. Сам API ничего не знает о чатах: вся связь между запросами и состоянием живёт в листенерах и thunks слоя `features`.
- **Гонка при выходе.** Базовый запрос кладёт `idInstance` в `meta` ответа. Если уведомление пришло уже после выхода или после входа в другой инстанс, listener его отбрасывает.
- **Чаты хранятся в слайсе, а не в кэше RTK Query.** Кэш RTK Query хранит только последний ответ очереди. Переписку собирают из многих уведомлений и дополняют локальными сообщениями, поэтому она живёт в `chatsSlice` (`entities/chat`).

- **Сопоставление ответов с чатом.** Сообщение уходит на `79991234567@c.us`, а ответ из MAX приходит с внутренним `chatId` (например, `10000000`). Чат ищется по `senderPhoneNumber`. Если номер скрыт (`0`), внутренний chatId берётся из `outgoingAPIMessageReceived` или статуса по `idMessage` отправленного сообщения. Все встреченные chatId запоминаются в `chat.chatIds`.
- **Порядок сообщений.** Сообщения показываются в порядке поступления, а не сортируются по `timestamp`. Очередь GREEN-API отдаёт уведомления строго по порядку (FIFO), а сравнение серверного времени (в секундах) с локальным временем отправки ломает порядок, если часы клиента и сервера расходятся.
- **Надёжность приёма.** Уведомление удаляется только после обработки. Если удаление не прошло, повторно полученное уведомление отбрасывается по `idMessage`.
